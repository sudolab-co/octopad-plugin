# Choosing how to deliver

## Prepare enough to choose how to deliver

- Identify the deliverables, settled choices, real dependencies, usable proof, required inputs, accesses and human interventions.
- Stay within the requested scope: outline only what matters now, and leave later details until their inputs exist.
- Keep this preparation on the owning stream and its tasks, with links to sources and existing confirmations. Keep no second brief or progress list.
- Record only lasting choices as Decisions; Octoplan keeps its plan on the tasks and the user's delivery mandate in a stream update.

- Evaluate the bounded work agents could actually finish and verify between human interventions, with the current tools and access, and compare that useful work with the cost of dispatch, handoffs and review. Decide by judgment, not by a task count, a duration threshold or an autonomy score.
- A few required review or production gates do not rule out useful agent work between them: keep every gate and its owner.
- When the next meaningful steps depend on repeated user choices, continue direct collaboration, and reconsider once those choices settle.
- Do not offer agent delivery on every turn.

- When useful agent delivery is plausible, open the `octoplan` skill to qualify the actual runtime route and have its draft plan reviewed.
- Before the user chooses how much autonomy agents get, show the Plan's summary: what agents can finish without the user, and every known intervention, access, proof and continuation limits included.
- Offer it in plain words: the user need not know the name Octoplan.
- Opening the `octoplan` skill or accepting a brief grants no delivery authority: delivery by Octoplan agents needs the user's explicit confirmation (What needs the user's confirmation first).
- When the benefit or the capability is unproved, continue authorized preparation or collaboration, name the concrete gap, and do not promise unattended delivery through it.

- Treat the request as planning-only when the user's request or context limits the outcome to a plan, such as "only the plan" or "we will decide whether to execute later". A missing mandate, or "create the stream/Octoplan" within a delivery discussion, does not set that limit.
- For an actual planning-only request, offer no delivery unless the user changes that scope.
- Respect an explicit pause or postponement.

## Keep the same work when delivery changes

When work moves from collaboration to agent delivery:
- Keep the same stream and task identities, decisions, evidence and progress.
- Carry forward a valid explicit brief confirmation; Octoplan checks its source and fills only the missing preparation and authority.
- A stream name or an existing graph proves neither a confirmation nor a mandate.
- Never restart completed work: a done task stays settled unless evidence contradicts its completion.

- Open a new stream only when the work's actual scope calls for one under [the stream rules](../SKILL.md#which-stream-work-belongs-to), never just to turn on agent delivery.
- On resume, check current state and ownership; an existing valid Octoplan follows its own resume rules, without a duplicate choice.
- Before work returns to direct collaboration, stop the delivery as the `octoplan` skill (section "Stop or hand over") says; never leave agents or pending effects running under a superseded mandate.
